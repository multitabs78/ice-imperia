# API личного кабинета

Единственный вход в систему. Веб-кабинет и будущие мобильные приложения
пользуются этими же адресами — своей логики у них нет. Правила, по которым
считаются абонементы и перерасчёты, описаны в [spec.md](spec.md), раздел 4;
здесь только как их вызвать.

---

## Общие правила

**Адрес.** `https://ice-imperia.ru/api/v1/…` Версия в пути нужна, потому что
приложения нельзя обновить у всех одновременно: когда появится `v2`, старая
версия продолжит работать.

**Формат.** Запрос и ответ — JSON в UTF-8. Для `GET` параметры идут в строке
запроса, для остальных методов — телом в JSON.

**Даты.** `2026-11-09` для дат, `16:30` для времени, `2026-11` для месяца
абонемента. Время отметок возвращается полностью: `2026-11-09T18:42:15+03:00`.

**Деньги.** Строкой с двумя знаками: `"14400.00"`. Не числом — двоичная
дробь не хранит рубли с копейками точно, и суммы в отчётах начинают
расходиться на копейку.

**Успешный ответ** — объект с данными. Список возвращается так:

```json
{
  "items": [ … ],
  "total": 94,
  "limit": 50,
  "offset": 0
}
```

**Ошибка** — всегда одинаковой формы, с кодом, пригодным для разбора,
и текстом, пригодным для показа человеку:

```json
{
  "error": "validation_failed",
  "message": "Проверьте заполненные поля",
  "fields": { "birth_date": "Дата рождения в будущем" }
}
```

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `bad_request` | Запрос не разобран |
| 401 | `unauthorized` | Нет токена или он истёк |
| 403 | `forbidden` | Роль не позволяет, либо это чужой спортсмен |
| 404 | `not_found` | Нет такой записи |
| 405 | `method_not_allowed` | Адрес есть, но не для этого метода |
| 409 | `conflict` | Правило не позволяет: абонемент на месяц уже выдан |
| 422 | `validation_failed` | Поля заполнены неверно, подробности в `fields` |
| 429 | `too_many_requests` | Слишком часто: коды входа, попытки пароля |
| 500 | `server_error` | Сбой на сервере, подробности только в лог |

**Авторизация.** Токен в заголовке `Authorization: Bearer …`. Веб-кабинет
получает тот же токен в cookie `cab_token` с флагами `HttpOnly`, `Secure`
и `SameSite=Lax` — так его не достанет чужой скрипт. Приложения хранят токен
средствами устройства.

**Границы доступа проверяются на сервере при каждом запросе,** а не прячутся
в интерфейсе. Тренер, запросивший чужую группу, получает `403` — даже если
обратится напрямую, минуя кабинет. Родитель видит только детей, привязанных
к нему в `parent_athlete`. Это не дублирование проверок из кабинета:
кабинет — лишь один из клиентов, и доверять ему нельзя.

## Вход

Три канала равноправны, механизм под ними один: одноразовый код с коротким
сроком жизни. Меняется только способ доставки, поэтому отключение канала
не затрагивает саму проверку.

### POST /auth/request-code

```json
{ "login": "+79990000000", "channel": "sms" }
```

`login` — телефон, почта или `telegram`. `channel` — `sms`, `email`
или `telegram`.

Ответ не говорит, существует ли такой пользователь: иначе перебором можно
собрать список клиентов школы.

```json
{ "sent": true, "channel": "sms", "expires_in": 300, "hint": "+7 999 ••• 00 00" }
```

Если канал `telegram`, а привязки нет, приходит `409` с кодом
`telegram_not_linked` и одноразовой ссылкой на бота.

### POST /auth/verify-code

```json
{ "login": "+79990000000", "code": "482104" }
```

Код из шести цифр. Четырёх хватило бы при пяти попытках, но шесть
ничего не стоят, а запас на порядки больше.

```json
{
  "token": "…",
  "expires_at": "2026-12-09T18:42:15+03:00",
  "user": { "id": 12, "name": "Иевлева Мария Петровна", "roles": ["parent"] }
}
```

Пять неверных попыток — код сгорает, нужен новый. Больше пяти запросов кода
с одного адреса за час — `429`.

### POST /auth/login

Для тренеров и администратора: `{ "login": …, "password": … }`. Ответ тот же.
Если в ответе `"must_change_password": true`, кабинет обязан отправить
на смену пароля до остальной работы.

### POST /auth/change-password

```json
{ "current_password": "…", "new_password": "…" }
```

Новый пароль — не короче восьми символов. В ответ приходит новый токен,
а все прежние закрываются: если пароль меняют потому, что его узнали,
чужая сессия не должна остаться рабочей.

### POST /auth/logout

Отзывает текущий токен. Параметр `"everywhere": true` — все токены
пользователя.

### GET /ping

Отвечает без всякой авторизации — по нему проверяют, что API развёрнут
и отвечает:

```json
{ "ok": true, "time": "2026-11-09T18:42:15+03:00" }
```

### GET /me

Кто вошёл, с ролями и правами. Кабинет строит по этому ответу меню,
а не угадывает роль:

```json
{
  "id": 12,
  "name": "Иевлева Мария Петровна",
  "roles": ["parent"],
  "children": [ { "id": 31, "name": "Иевлев Пётр" } ]
}
```

## Справочники

Только администратор. Везде одинаковый набор: `GET` список с `?q=` для поиска
и `?status=`, `POST` создание, `GET /{id}`, `PATCH /{id}` изменение.
Записи не удаляются, а уходят в архив: `PATCH` со `"status": "archived"`.

| Адрес | Что |
|---|---|
| `/athletes` | спортсмены |
| `/athletes/{id}/parents` | привязка родителей: `POST` `{parent_user_id, relation, is_primary}` |
| `/parents` | родители — пользователи с ролью `parent` |
| `/coaches` | тренеры |
| `/groups` | группы |
| `/groups/{id}/coaches` | кто ведёт группу |
| `/enrollments` | назначения в группы |
| | `/tariffs` | тарифы, в том числе варианты с `days_per_week` |
| `/tariffs/{id}/extras` | какие дополнительные занятия входят в тариф |
| `/extra-classes` | дополнительные занятия: название, вид, разовая цена |
| `/discounts` | справочник скидок |
| `/discounts/{id}/scopes` | на какие группы и тарифы действует скидка |
| `/groups/{id}/schedule` | постоянное расписание группы |
| `/schedule-rules/{id}` | одно правило расписания |
| `/schedule/generate` | раскрытие правил в тренировки |
| `/ranks` | разряды |
| `/lesson-kinds` | виды занятий |
| `/athletes/{id}/schedule` | постоянные индивидуальные занятия |
| `/venues`, `/spots` | спорткомплексы и площадки внутри них |
| `/coaches/{id}/handover` | передача групп другому тренеру |
| `/trainings` | тренировки, отмена, перенос, замена тренера |
| `/trainings/{id}/attendance` | лист отметок и сохранение |
| `/trainings/{id}/makeup` | отработка пропуска |
| `/groups/{id}/attendance` | журнал группы за месяц |
| `/athletes/{id}/attendance` | история посещений спортсмена |
| `/services` | услуги и цены |
| `/users` | учётные записи — для привязки карточки тренера |
| `/settings` | числа из таблицы настроек, кроме цен |

Удалить спортсмена по требованию о персональных данных — не `DELETE`:
`POST /athletes/{id}/anonymize` затирает имя и дату рождения, отвязывает
родителей и уводит профиль в архив, оставляя обезличенную статистику
посещений и абонементов. Иначе рассыплются прошлые отчёты. Поле `reason`
обязательно: действие необратимое.

### Кто что видит в списках

`GET /athletes` и `GET /groups` отдают разное в зависимости от роли,
и это решает сервер, а не интерфейс:

- администратор — всех и все;
- тренер — спортсменов своих групп и только свои группы;
- родитель — своих детей.

Запрос чужой группы или чужого спортсмена возвращает `403`, даже если
обратиться в обход кабинета. У `/athletes` есть `?q=` для поиска по фамилии
и имени, `?group_id=`, `?status=` (`active`, `archived`, `all`),
`?limit=` и `?offset=`.

### POST /enrollments

```json
{ "athlete_id": 31, "group_id": 4, "date_from": "2026-11-01" }
```

```json
{ "enrollment_id": 88, "closed": 1, "groups": [ … ] }
```

Сервер сам закрывает прошлое назначение днём раньше перехода — история
остаётся. Перевели в мае, и осенний отчёт по-прежнему знает, что до мая
ребёнок был в другой группе. Повторное назначение в ту же группу
отклоняется с `409 already_enrolled`.

### Тарифы меняются версиями

`PATCH /tariffs/{id}` правит название, состав и состояние. Но если
по тарифу уже выдан хоть один абонемент, цену, число занятий и вариант
менять нельзя — `409 tariff_in_use`. Иначе прошлогодний отчёт пересчитался бы
по сегодняшним ценам, а у родителя в кабинете выросла бы сумма давно
оплаченного абонемента.

Для новой цены есть `POST /tariffs/{id}/revise`: создаёт новую версию,
прежнюю уводит в архив и переключает на неё группы. Выданные абонементы
остаются со своими суммами.

### POST /coaches

```json
{ "last_name": "Филь", "first_name": "Всеволод",
  "email": "coach@example.ru", "password": "временный" }
```

Пароль необязателен: без него создаётся карточка тренера без входа
в кабинет. С паролем сразу заводится учётная запись, и при первом входе
система потребует задать свой — временный пароль знает не только тренер.

Перевод тренера в архив (`PATCH` со `"status": "archived"`) закрывает
и его вход: учётная запись блокируется, все токены отзываются.

### Карточка спортсмена

Кроме имени и даты рождения в ней живут даты зачисления и отчисления,
разряд с документом о присвоении и сроки допусков:

```json
{ "joined_at": "2026-09-01", "left_at": null,
  "rank_id": 3, "rank_name": "2 юношеский",
  "rank_date": "2026-03-15", "rank_doc": "Приказ № 114-с",
  "medical_until": "2026-11-29", "medical_left": 40,
  "insurance_until": "2026-10-17", "insurance_left": -3 }
```

Запас в днях считает сервер, а не каждый клиент по-своему. Отрицательное
число означает, что срок уже вышел.

Дата зачисления проставляется сама в день заведения карточки: пустая графа
хуже разумного умолчания. Дата отчисления ставится при обезличивании
профиля и при переводе в архив, а возврат в работу её снимает — два поля
об одном и том же не должны расходиться.

`GET /ranks`, `POST /ranks`, `PATCH /ranks/{id}` — список разрядов.
Он задан спортивной классификацией, но лежит в справочнике: школа добавит
МСМК сама, без правки кода.

### Виды занятий

`GET /lesson-kinds`, `POST /lesson-kinds`, `PATCH /lesson-kinds/{id}`.

Был жёсткий перечень из трёх значений — лёд, зал, хореография. Школа
добавляет ОФП, растяжку, прыжковую, и каждый раз это была бы правка кода.
Расписание ссылается на `kind_id`. Вид, по которому ещё стоят будущие
занятия, в архив не убрать: `409 kind_in_use`.

### Индивидуальные занятия

Занятие с одним спортсменом вместо группы. Отдельной сущности не заводят:
иначе пришлось бы дублировать отмену, перенос, замену тренера и отметки.
У такого занятия `group_id` пустой, а `athlete_id` заполнен.

Разовое — обычный `POST /trainings` с `athlete_id` вместо `group_id`.
Указать оба сразу нельзя. Постоянное — `POST /athletes/{id}/schedule`,
устроенное так же, как расписание группы; раскрывается той же генерацией
(`POST /schedule/generate` принимает `athlete_id`).

В выдаче такое занятие помечено `personal: true`, а поле `title`
подписывает его именем спортсмена вместо кода группы. Лист отметок
на нём состоит из одного человека — того, ради кого оно назначено.

Уникальный ключ базы здесь не помогает: у личных занятий `group_id` пустой,
а два пустых значения база считает разными. Поэтому занятость времени
проверяется в коде — по группе либо по спортсмену.

### Спорткомплексы и площадки

`GET /venues` отдаёт комплексы вместе с их площадками. `POST /venues`,
`PATCH /venues/{id}` — комплекс; `POST /venues/{id}/spots`,
`PATCH /spots/{id}` — площадка внутри него.

```json
{ "id": 1, "name": "Ледовая арена «Гололёд»", "address": "…",
  "spots": [ { "id": 1, "name": "Лёд", "kind": "ice" },
             { "id": 2, "name": "Зал 2", "kind": "hall" } ] }
```

Расписание ссылается на **площадку** (`spot_id`); комплекс следует за ней
сам, отдельно его задавать не нужно — два поля рано или поздно разъехались
бы. Площадку, на которой ещё стоят будущие занятия, в архив не убрать:
`409 spot_in_use`.

### Кто кому мешает

Одну площадку несколько групп делят свободно: на одном льду одновременно
работает несколько тренеров, и в зале тоже. Занятость считается только
по человеку, и только когда он оказался бы в **двух разных местах** сразу.
Две группы у одного тренера на одной площадке — это объединённое занятие,
а не ошибка.

### Расписание: правило и тренировка — разные вещи

Правило — шаблон: «СОГ-1, по понедельникам в 17:00, лёд, Гололёд, с 1 сентября».
Тренировка — факт: занятие конкретного дня, которое можно отменить, перенести
и на котором тренер отмечает посещения.

Правка правила **никогда не переписывает уже созданные тренировки задним
числом**. Иначе смена расписания в январе переписала бы сентябрь, а вместе
с ним и отмеченные посещения.

`GET /groups/{id}/schedule` — правила группы, по умолчанию действующие,
с `?all=1` — вместе с закрытыми.
`POST /groups/{id}/schedule`:

```json
{ "weekday": 1, "time_start": "17:00", "duration_min": 60,
  "kind": "ice", "venue_id": 1, "coach_id": 3, "valid_from": "2026-09-01" }
```

`weekday` — от 1 (понедельник) до 7 (воскресенье). `kind` — `ice`, `gym`
или `choreo`. Повтор того же дня и времени у той же группы отклоняется
с `409 rule_exists`.

`PATCH /schedule-rules/{id}` правит шаблон. По умолчанию уже созданные
занятия остаются как были. С `apply_from` изменение переносится и на
**запланированные** занятия с этой даты — ради того, ради чего правка
обычно и затевается:

```json
{ "coach_id": 7, "apply_from": "2026-11-01", "reason": "Уволился прежний" }
```
```json
{ "…": "…", "applied": 12, "clashes": [] }
```

Проведённые, отменённые и перенесённые не трогаются никогда. Занятия,
которые не удалось перенести из-за накладки, перечисляются в `clashes`,
остальные переносятся.

`POST /coaches/{id}/handover` передаёт **все** группы, правила расписания
и будущие занятия другому тренеру одним действием:

```json
{ "to_coach_id": 7, "from_date": "2026-11-01", "reason": "Уволился" }
```

Проведённые занятия остаются за тем, кто их провёл: по ним считаются
выплаты.

`DELETE /schedule-rules/{id}?from=`
закрывает его: физически не удаляет (на правило ссылаются прошедшие
тренировки), ставит `valid_to` днём раньше и снимает **запланированные**
занятия с этой даты. Проведённые и отменённые остаются.

### POST /schedule/generate

Раскрывает правила в конкретные занятия.

```json
{ "group_id": 4, "weeks": 8, "from": "2026-11-01" }
```
```json
{ "from": "…", "to": "…", "created": 16, "existed": 4,
  "skipped": [ { "group": "НП-1", "date": "2026-11-03", "time": "17:00",
                 "reason": "В это время на льду уже занимается СОГ-1" } ] }
```

Повторный запуск безопасен: занятие, уже существующее в тот же день и время,
пропускается — что бы с ним ни делали. Отменённое не воскресает, отметки
не пропадают.

Накладки не прерывают генерацию: система создаёт всё остальное и перечисляет,
что не поместилось. Занятым считается тот же лёд на той же площадке или тот же
тренер в то же время; зал и хореография ко льду не ревнуют — это разные
помещения.

### Тренировки

`GET /trainings?from=&to=&group_id=&status=&mine=1` — список за период.
Роль решает, что попадёт в выдачу: администратор видит всё, тренер — свои
группы **и те занятия, на которые его назначили заменять**, родитель —
группы своих детей.

`GET /trainings/{id}` добавляет состав группы **на день тренировки**, а не
на сегодня: кто занимался тогда, тот и должен быть в списке.

`POST /trainings` заводит разовое занятие вне расписания.

`POST /trainings/{id}/cancel` — `reason` обязателен. Проведённое занятие
не отменяется: `409 training_held`. Отменённое остаётся в расписании
с пометкой — школа должна его перенести или вернуть бонусным.

`POST /trainings/{id}/move` создаёт новое занятие и помечает прежнее
`moved` со ссылкой `moved_to_training_id`. Прежнее не удаляется, иначе
пропадёт след, что школа перенесла, а не отменила.

`POST /trainings/{id}/coach` назначает тренера на занятие — замену.
Может администратор **и тренер самой группы**: когда он понимает, что
не придёт, ему незачем дожидаться администратора. Занятие потом считается
тому, кто вёл, а не тому, за кем закреплена группа.

### Отметки посещаемости

Отметка — это факт. Она записывается независимо от состояния абонемента:
ребёнок на льду был, и школа должна видеть это сразу, а не через месяц.
Деньги считает отдельный модуль, по полю `charged`.

`GET /trainings/{id}/attendance` — лист отметок:

```json
{ "training_id": 12, "date": "2026-11-03", "can_mark": true, "closed_why": null,
  "window_days": 3,
  "items": [ { "athlete_id": 31, "name": "Петров Илья", "makeup": false,
               "mark": { "status": "present", "label": "был", "charged": true } } ] }
```

Состав берётся **на дату тренировки**, а не на сегодня: кто занимался тогда,
тот и должен быть в списке, даже если потом ушёл. Отмеченные, но не из состава —
отработки из других групп; их тоже видно.

`POST /trainings/{id}/attendance` принимает **весь лист разом**:

```json
{ "reason": "Опоздала, но была",
  "marks": [ { "athlete_id": 31, "status": "present" },
             { "athlete_id": 32, "status": "absent" } ] }
```

Тренер у борта отмечает группу одним действием, и половина сохранённого
листа хуже, чем ничего. `reason` обязателен только когда меняется уже
сохранённая отметка: при первой отметке вопрос был бы лишней помехой.
Отмеченное занятие становится `held`, после чего его нельзя отменить
или перенести.

Что списывается, решает одно место в коде:

| Отметка | Списано |
|---|---|
| был | да |
| пропуск | да |
| пропуск по болезни | да |
| отменено школой | нет |
| отработка | нет |

Пропуск списывает независимо от того, предупредили или нет: правило одно.
Болезнь тоже списывает — право на перерасчёт разбирается деньгами и отдельно.

### Когда отмечать нельзя

`can_mark: false` и `409 marking_closed` при попытке. Причины: занятие ещё
не прошло, отменено, перенесено, либо у тренера истекло окно правки
(`coach_edit_window_days`, по умолчанию трое суток). Администратора окно
не ограничивает — иначе смысл в сроках пропадает, но исправить ошибку
становится некому.

### Отработка

`POST /trainings/{id}/makeup`:

```json
{ "athlete_id": 31, "missed_training_id": 9, "comment": "Согласовано с тренером" }
```

Занятие не списывается — пропуск уже списан раньше, и списать второй раз
значило бы взять дважды. Сервер проверяет, что на указанном занятии
действительно стоит пропуск (`409 not_a_miss`) и что он ещё не отработан
(`409 already_made_up`).

`DELETE /attendance/{id}?reason=` снимает **только отработку**. Обычная
отметка не удаляется, а исправляется: `409 not_a_makeup`.

### Журнал

`GET /groups/{id}/attendance?month=2026-11` — то, что сейчас ведётся
в таблице: занятия по столбцам, спортсмены по строкам, итоги по каждому
(был, пропусков, списано).

`GET /athletes/{id}/attendance?from=&to=` — история одного спортсмена.

### Услуги и цены

`GET /services?status=all`, `POST /services`, `PATCH /services/{id}` —
только администратор.

```json
{ "id": 1, "code": "single_lesson", "name": "Разовое занятие без абонемента",
  "price": "2500.00", "price_set": true, "system": true,
  "note": "По этой цене считается перерасчёт по болезни и долг за месяц без абонемента" }
```

Непустой `code` помечает услугу, на которую ссылается расчёт: `system: true`,
её нельзя убрать в архив — `409 service_is_system`. Название и цену менять
можно. Услуги без кода школа заводит сама: прокат, заточка, индивидуальное
занятие.

`price_set: false` означает, что цена не задана. Это не ноль: начисление
по такой услуге отвечает `409 price_not_set` и называет услугу, вместо того
чтобы молча списать ничего.

### Один человек в двух ролях

`POST /coaches` принимает `user_id` — тогда карточка тренера привязывается
к существующей учётной записи, а не создаётся новая. Так администратор
школы, который сам тренирует, входит одним логином и получает обе роли.
Если к учётной записи уже привязана карточка тренера — `409 user_is_coach`.

Список тех, к кому можно привязать: `GET /users?free_coach=1`.

### PATCH /settings

Числа из таблицы настроек — порог болезни в днях, окно правки отметок,
горизонт генерации расписания, предел суммарной скидки. Цены сюда больше
не входят, они в справочнике услуг:

```json
{ "single_lesson_price": "2600", "reason": "Цены с января" }
```

Меняются только известные имена, пустое значение не сохраняется,
каждое изменение попадает в журнал вместе с прежним значением.

## Расписание

### Постоянное расписание

`GET`, `POST`, `PATCH`, `DELETE /schedule-rules`.

```json
{
  "group_id": 4,
  "weekday": 2,
  "time_start": "16:30",
  "duration_min": 60,
  "kind": "ice",
  "extra_class_id": null,
  "venue_id": 1,
  "coach_id": 3,
  "valid_from": "2026-09-01"
}
```

`weekday` — 1 понедельник … 7 воскресенье. `kind` — `ice`, `gym`, `choreo`.

`extra_class_id` решает, занятие это или дополнительное. Пусто — основное,
оно считается в абонементе. Заполнено — зал или хореография тем же днём:
такое занятие остатка не трогает, а для тех, у кого оно в абонемент
не входит, начисляется по цене из справочника. Этим же полем правится
количество и время дополнительных занятий — через обычное расписание.

Правило меняют не правкой, а закрытием: `PATCH` с `valid_to` и новое правило
с `valid_from`. Так прошедшие недели остаются такими, какими были.

### POST /schedule/generate

Создаёт конкретные тренировки из правил.

```json
{ "from": "2026-11-01", "to": "2026-12-31", "group_id": 4 }
```

```json
{ "created": 26, "skipped": 4, "horizon_weeks": 8 }
```

Повторный запуск за тот же период ничего не портит: у тренировок стоит
уникальность по группе, дате и времени, и совпадения попадают в `skipped`.
Без `group_id` — по всем группам.

### GET /trainings

`?from=`, `?to=`, `?group_id=`, `?coach_id=`, `?status=`.
Тренер без `coach_id` получает свои; с чужим — `403`.

### PATCH /trainings/{id}

Смена тренера, времени, отмена:

```json
{ "status": "cancelled", "cancel_reason": "Заливка льда", "reason": "Сообщили с арены" }
```

Отмена не списывает занятия ни у кого из группы и ставит всем посещениям
статус `cancelled`.

### POST /trainings/{id}/move

Перенос — основной способ закрыть отменённую тренировку.

```json
{ "date": "2026-11-15", "time_start": "19:00", "reason": "Перенос с 12 ноября" }
```

Создаёт новую тренировку, прежней ставит `moved` и ссылку
`moved_to_training_id`. В расписании и у родителя видно, куда она ушла,
а не то, что занятие пропало.

Если переносить некуда — `POST /trainings/{id}/compensate` оформляет
бонусные занятия на следующий абонемент всем, кто был записан.

## Посещаемость

Основная работа тренера, и самая частая операция в системе.

### GET /trainings/{id}/roster

Список группы на конкретную тренировку, с тем, что уже отмечено:

```json
{
  "training": {
    "id": 812, "date": "2026-11-11", "time_start": "16:30",
    "kind": "ice", "extra_class": null,
    "group": { "id": 4, "code": "СОГ-2" }, "status": "planned"
  },
  "editable_until": "2026-11-14T23:59:59+03:00",
  "athletes": [
    {
      "id": 31, "name": "Иевлев Пётр",
      "attendance": null,
      "covered": true,
      "subscription": { "id": 55, "sessions_left": 3, "period": "2026-11" }
    },
    {
      "id": 32, "name": "Смирнова Анна",
      "attendance": { "status": "present", "charged": true },
      "covered": false,
      "subscription": null,
      "warning": "no_subscription",
      "price_if_attends": "2500.00"
    }
  ],
  "not_expected": [
    { "id": 33, "name": "Петров Илья", "reason": "day_not_in_subscription" }
  ]
}
```

**Состав списка зависит от выбранных дней.** В `athletes` попадают те, чей
абонемент покрывает именно этот день: у СОГ-2 четыре занятия в неделю,
и спортсмен с вариантом на три в своём «пропущенном» дне не ожидается.
Остальные уходят в `not_expected` — отдельным списком, а не вперемешку:
тренер должен видеть тех, кого ждёт, но иметь возможность отметить
и пришедшего не в свой день. Такое посещение станет либо отработкой,
либо начислением по разовой цене.

`covered` говорит, покрыто ли посещение абонементом, `price_if_attends` —
во что оно обойдётся, если нет. Для дополнительного занятия (`extra_class`
заполнен) `covered` зависит от того, входит ли оно в тариф спортсмена,
а цена берётся из справочника дополнительных занятий, не из ставки 2 500 ₽.

Ни `covered: false`, ни `warning` не мешают отметить посещение. Тренер
отмечает факт, а не состояние счёта: ребёнок на льду был, и школа должна
увидеть это сразу, а не через месяц.

### POST /trainings/{id}/attendance

Вся группа одним запросом — тренер отмечает список целиком, а не по одному:

```json
{
  "records": [
    { "athlete_id": 31, "status": "present" },
    { "athlete_id": 32, "status": "absent" },
    { "athlete_id": 33, "status": "absent_sick", "comment": "Сообщила мама" }
  ]
}
```

```json
{
  "saved": 3,
  "charged": 2,
  "records": [
    { "athlete_id": 31, "status": "present",     "charged": true,  "subscription_id": 55 },
    { "athlete_id": 32, "status": "absent",      "charged": true,  "subscription_id": 56 },
    { "athlete_id": 33, "status": "absent_sick", "charged": true,  "subscription_id": 57 }
  ]
}
```

Списание считает сервер, кабинет его не передаёт. Пропуск списывает занятие
независимо от предупреждения — правило 9. Повторная отправка перезаписывает
отметки, пока не вышло окно правки (`editable_until`, по умолчанию трое
суток); позже — `403 edit_window_closed`, и правит уже администратор.

### POST /attendance/makeup

Отработка, согласованная тренером. Не списывается: закрывает уже списанный
пропуск, а не добавляет новый расход.

```json
{ "athlete_id": 31, "training_id": 830, "makeup_for_training_id": 812 }
```

Сервер проверит, что по закрываемой тренировке у спортсмена действительно
есть списанный пропуск. Иначе `409 nothing_to_make_up` — иначе отработками
можно было бы получить бесплатные занятия.

### GET /athletes/{id}/attendance

`?from=`, `?to=`. Тренеру доступны свои спортсмены, родителю — свои дети,
администратору — все.

## Абонементы и деньги

Самая чувствительная часть: здесь считаются суммы, которые назовут родителю.
Поэтому у выдачи и перерасчёта есть предпросмотр — отдельный адрес, который
ничего не меняет, а показывает арифметику.

### GET /subscriptions/preview

```
?athlete_id=31&group_id=4&tariff_id=2&period=2026-11&date_from=2026-11-10
   &rule_ids=17,18,21
```

```json
{
  "period": "2026-11",
  "date_start": "2026-11-01",
  "date_end": "2026-11-30",
  "tariff": {
    "id": 2, "name": "СОГ-2, 3 занятия в неделю",
    "price": "20000.00", "sessions_count": 12, "days_per_week": 3
  },
  "slots": [
    { "rule_id": 17, "weekday": 1, "time_start": "17:30" },
    { "rule_id": 18, "weekday": 3, "time_start": "17:45" },
    { "rule_id": 21, "weekday": 7, "time_start": "19:00" }
  ],
  "lesson_price": "1666.67",
  "sessions_in_month": 13,
  "sessions_counted": 8,
  "price_base": "13333.00",
  "discounts": [
    { "discount_id": 1, "name": "Скидка на второго ребёнка",
      "kind": "percent", "value": "30.00", "amount": "4000.00", "auto": true }
  ],
  "price": "9333.00",
  "credit_in": "4400.00",
  "due": "4933.00",
  "explain": "20000 × 8 ÷ 12 = 13333 ₽, скидка 30% — 4000 ₽, зачтено 4400 ₽ с октября"
}
```

`rule_ids` — выбранные дни. Обязательны, когда `days_per_week` тарифа меньше
числа занятий в расписании группы: иначе `422 slots_required`. Передано
не столько, сколько в варианте, — `422 slots_count_mismatch`.

`sessions_counted` — занятия выбранных дней с `date_from` до конца месяца;
без `date_from` считается весь месяц. Считаются только основные занятия:
зал и хореография в число не входят.

`discounts` приходит заполненным и без запроса: скидка на второго ребёнка
определяется автоматически. Администратор может добавить ручную скидку,
передав `discount_ids`, или убрать автоматическую — `"skip_auto_discounts": true`.

Считается в одно действие с округлением в конце. При делении сначала
у неровных ставок набегают копейки: 20 000 ÷ 12 = 1 666,67, и на тринадцати
занятиях выходит 21 666,71 вместо 21 666,67.

### POST /subscriptions

Те же поля. Сервер считает цену сам и игнорирует присланную: иначе
подменённый запрос выдал бы абонемент за любую сумму.

Абонемент на месяц у спортсмена в группе один — повторная выдача даёт
`409 subscription_exists`.

### GET /athletes/{id}/subscriptions

История с остатками. Остаток считается, а не хранится:

```json
{
  "items": [
    {
      "id": 55, "period": "2026-11", "group": "СОГ-1",
      "price": "16200.00", "paid": "16200.00", "credit_in": "0.00",
      "sessions_total": 9, "sessions_bonus": 0, "sessions_charged": 6,
      "sessions_left": 3, "status": "active",
      "date_start": "2026-11-01", "date_end": "2026-11-30"
    }
  ]
}
```

Кончившийся остаток абонемент не закрывает: до последнего числа месяца
он действует, даже когда тренировок в нём больше нет.

### POST /payments

Оплата привязывается к начислению, а не к абонементу: начислением может быть
и разовое занятие, и дополнительное.

```json
{ "athlete_id": 31, "charge_id": 204, "amount": "9333.00",
  "method": "cash", "paid_at": "2026-11-05" }
```

`charge_id` можно не передавать — тогда это аванс: деньги получены раньше,
чем выставлен абонемент. Такая оплата уменьшает общую задолженность
спортсмена и позже привязывается к начислению.

### GET /athletes/{id}/charges

Реестр начислений и оплат — то, из чего считается долг:

```json
{
  "items": [
    { "id": 204, "kind": "subscription",   "period": "2026-11",
      "amount": "9333.00",  "comment": "СОГ-2, 8 занятий, скидка 30%" },
    { "id": 211, "kind": "extra_drop_in",  "period": "2026-11",
      "amount": "900.00",   "training_id": 844, "comment": "Хореография 14 ноября" },
    { "id": 219, "kind": "recalculation",  "period": "2026-12",
      "amount": "-6200.00", "comment": "Перерасчёт по болезни за ноябрь" }
  ],
  "charged": "4033.00",
  "paid": "9333.00",
  "balance": "-5300.00"
}
```

Отрицательный `balance` — переплата, положительный — долг.

### GET /recalculations/preview

Перерасчёт по болезни. Сначала арифметика, потом оформление:

```json
{
  "subscription_id": 55,
  "illness_from": "2026-11-10",
  "illness_to": "2026-11-25",
  "days": 16,
  "threshold_days": 14,
  "eligible": true,
  "attended_sessions": 4,
  "rate": "2500.00",
  "attended_cost": "10000.00",
  "price": "16200.00",
  "amount": "6200.00",
  "explain": "16200 − 4 × 2500 = 6200 ₽ в счёт абонемента на декабрь"
}
```

Когда сумма выходит нулевой или отрицательной, `eligible` равно `false`,
а `reason` — `nothing_to_recalculate`, с той же арифметикой. Перерасчёт
в таком случае не оформляется вовсе, и право на него не считается
использованным: ставка 2 500 ₽ выше занятия в любом абонементе, поэтому
при шести посещениях в СОГ-1 к зачёту уже ничего не остаётся.

### POST /recalculations

```json
{
  "subscription_id": 55,
  "illness_from": "2026-11-10",
  "illness_to": "2026-11-25",
  "has_medical_document": true,
  "has_application": true,
  "comment": "Справка № 4821 от 26.11"
}
```

Отказы: `422 documents_required` без обеих отметок, `409 already_recalculated`
на второй раз за один абонемент, `409 nothing_to_recalculate` при нулевой
сумме, `422 below_threshold` при болезни короче порога.

### GET /debts

Задолженность — начисления минус оплаты, с разбивкой по источникам:

```json
{
  "total": "24600.00",
  "items": [
    {
      "athlete": { "id": 32, "name": "Смирнова Анна" },
      "charged": "24600.00",
      "paid": "0.00",
      "debt": "24600.00",
      "by_kind": {
        "subscription":    "16200.00",
        "no_subscription": "7500.00",
        "extra_drop_in":   "900.00",
        "recalculation":   "0.00"
      }
    }
  ]
}
```

`?period=2026-11` — долг за месяц, без параметра — весь накопленный.

## Кабинет родителя

Те же данные, но без права назвать чужой `athlete_id`. Отдельные адреса,
чтобы невозможно было перебрать номера:

| Адрес | Что |
|---|---|
| `GET /my/children` | дети с активными абонементами и остатками |
| `GET /my/children/{id}` | профиль ребёнка |
| `GET /my/children/{id}/attendance` | посещения, пропуски, отработки |
| `GET /my/children/{id}/subscriptions` | абонементы, перерасчёты, оплаты |
| `GET /my/schedule` | расписание детей, с переносами |
| `GET /my/debts` | задолженность |
| `GET /my/notifications` | уведомления |

`{id}` не в списке детей — `403`, а не `404`: чужой номер не должен отличаться
в ответе от несуществующего.

## Отчёты и журнал

Только администратор.

| Адрес | Что |
|---|---|
| `GET /reports/attendance?period=2026-11` | явка по группам и спортсменам |
| `GET /reports/money?period=2026-11` | начислено, оплачено, зачтено, долг |
| `GET /reports/coach-sessions?period=2026-11` | проведённые тренировки и явка по тренерам — основа расчёта выплат |
| `GET /audit?entity=subscription&entity_id=55` | журнал операций по записи |

`?format=csv` отдаёт таблицу файлом — для сверки с Google Таблицами
на первом этапе и для расчёта выплат тренерам.

### Исправления

Ошибочные операции не удаляются, а сторнируются: появляется обратная запись,
обе остаются в истории. Любое исправление требует `reason` — без причины
операция не сохраняется, и в журнале остаётся не только что изменилось,
но и зачем.

```json
{ "status": "absent", "charged": false, "reason": "Ошибка тренера, ребёнок был на тренировке" }
```

## Что уже работает

Ядро, вход, справочники, расписание и посещаемость написаны и проверены: `api/index.php` с маршрутизацией, ядро
в `api/core` — ответы и ошибки единого формата, обёртка над базой, проверка
токена и границ доступа, валидация, журнал, отправка кодов, — модуль
входа `api/modules/auth.php` и модуль справочников
`api/modules/directory.php` — спортсмены, родители и привязка детей,
тренеры, группы и их тренеры, назначения, площадки, тарифы, настройки,
и модуль расписания `api/modules/schedule.php` — постоянное расписание,
генерация тренировок, отмена, перенос, замена тренера, и модуль
посещаемости `api/modules/attendance.php` — лист отметок, исправления
с причиной, окно правки для тренера, отработки, журнал за месяц.

Проверка прогоняется одной командой из корня проекта:

```
php tests/run.php
```

Она поднимает встроенный сервер PHP на тестовой базе SQLite и ходит
по настоящим адресам настоящими запросами: 261 проверка — вход паролем
и кодом, просроченный код, перебор попыток, выход, смена пароля, создание
и правка записей справочников, перевод между группами с закрытием прошлого
назначения, версионирование тарифа, границы доступа тренера и родителя,
обезличивание профиля, записи в журнале, расписание: повторная генерация,
накладки по льду и тренеру, отмена и перенос, доступ заменяющего тренера,
отметки: что списывается, исправление только с причиной, окно правки,
отработки, журнал, площадки внутри комплексов, правка расписания
с переносом на занятия, передача групп новому тренеру, разряды и сроки
допусков, виды занятий как справочник, индивидуальные занятия. Ни MySQL, ни интернета
для этого не нужно; схема берётся из той же единственной миграции
и переводится на диалект SQLite на лету.

## Что будет дальше

Этого описания достаточно для первого этапа: вход, справочники, расписание,
посещаемость. Абонементные адреса описаны здесь же, хотя делаются вторым
этапом, — чтобы структура базы и формат ответов не пришлось потом менять
из-за того, что о них вспомнили позже.

Не хватает пока уведомлений (`POST /notifications/test`, отправка очереди
по расписанию) и привязки Telegram — они появятся вместе с третьим этапом.
